## Notes and decisions

- **Phase 1 data month:** 2025-01 chosen (file exists, 59,158,238 bytes, includes `cbd_congestion_fee`). One month only, per project rules.
- **Phase 1 observation (for Phase 2):** bronze `tpep_pickup_datetime` ranges from 2024-12-31 20:47:55 to 2025-02-01 00:00:44, so the file holds pickups outside January. These must go to quarantine in silver, not be dropped. Not acted on in Phase 1.
- **Phase 1 weather:** `scripts/fetch_weather.py` flattens Open-Meteo's column arrays into one JSON line per hour before landing (the raw API response is also kept locally). This is the only reshape before bronze. 744 rows = 31 days x 24 hours.
- **Phase 2 rules/assumptions:** reason codes are NEGATIVE_FARE, ZERO_DISTANCE, NEGATIVE_DISTANCE, PICKUP_OUTSIDE_MONTH (month taken from the source file name; start inclusive, end exclusive), DROPOFF_BEFORE_PICKUP and NULL_TIMESTAMP. Missing `passenger_count` stays NULL in silver (not a rule). Exact duplicates are removed before validation and counted (0 in 2025-01).
- **Phase 2 observation:** NEGATIVE_FARE is by far the largest reason (144,118 rows). Whether these are genuine refunds/adjustments rather than errors was not investigated; they are quarantined with original values so they can be reviewed, not dropped. NEGATIVE_DISTANCE and NULL_TIMESTAMP matched 0 rows this month (no code appears in the breakdown).
- **Phase 2 setup incident:** the first silver job run (batch `s1`) succeeded but auto-created `silver.trips` without CHECK constraints, because Databricks rejects inline CHECK in `CREATE TABLE`. Both silver tables (created by this project minutes earlier) were dropped and recreated from `sql/20_silver_tables.sql` (constraints added with `ALTER TABLE`), then re-run as `s2`/`s3`. The `s1` output is not used for any figure here.
- **Phase 3 design:** `trip_key` = SHA-256 of JSON of all 20 source columns plus source file (null-safe; unique because silver removes exact duplicates). Weather is attached by a LEFT join on the pickup hour, so a trip is never lost for missing weather (0 trips lacked weather in 2025-01). Dimensions are rebuilt each run; `dim_date` spans all silver dates so a later backfill cannot drop earlier months. Re-running a month MERGEs on `trip_key`.
- **Phase 3 limitation (resolved in Phase 4 by the `row_hash` conditional MERGE, see below):** the MERGE updated every matched row on a re-run (3,254,520 updates in `g2`) even though nothing changed; results are identical but the work is not minimal. A change-detection condition could be added in Phase 4 if runtime matters.
- **Phase 3 re-verification (2026-10-25, re-queried):** counts, keys, orphans, sums, aggregates and weather coverage were re-checked by SQL and matched the recorded figures; `DESCRIBE HISTORY gold.fact_trips` also shows a version 3 `OPTIMIZE` that Databricks ran automatically after the `g2` MERGE (no data change). `pytest` 46 passed; `bundle validate -t dev` OK.
- **Phase 3 incident:** the first gold job run failed (run 129681121958037, `TABLE_OR_VIEW_NOT_FOUND` for `gold.fact_trips`) because my SQL runner split `sql/30_gold_tables.sql` on a semicolon inside a table comment, so `fact_trips` was not created. It had already rebuilt the four dimensions; no fact or aggregate rows were written. The comment was fixed, tables were created, and the job re-ran as `g1`. Figures above come only from `g1`/`g2`.
- **Phase 4 range and scope:** backfilled **2025-01 to 2025-06 (6 months)** by user decision, driven month by month from the laptop (`scripts/backfill.py`); no other month has been ingested. Landing stays on the laptop, so the `taxilake_pipeline` monthly schedule is defined but PAUSED: a scheduled run would fail at bronze unless that month's files were already uploaded.
- **Phase 4 MERGE change:** `fact_trips.row_hash` (xxhash64 of the row content, excluding `_batch_id`) was added by `sql/31_migrate_fact_row_hash.sql`; the MERGE now updates only rows whose hash changed. One-off: run `g3` populated the hashes (3,254,520 updated, 125.8 s); run `g4` then updated 0 rows. `_batch_id` on an unchanged fact row therefore stays at the last batch that changed it.
- **Phase 4 incidents:** (1) the first `checks` run failed (3 task attempts, then the job) because the fingerprint sums (decimal(38,0)) overflowed when round-tripped through Python `createDataFrame`; fixed by keeping them in Spark, then re-run. That failed run is in `data/backfill_log.jsonl` (local, gitignored) and not used for any figure. (2) `ADD COLUMN IF NOT EXISTS` is not supported, so the row_hash migration is a separate run-once file. (3) My SQL runner split a table comment on a semicolon again; comment fixed. (4) Upload now skips identical files (same name and size) so a re-run cannot re-timestamp a loaded file; `--force` overrides.
